# GPL runtime overlay — source, evidence and current limits

The owner-supplied recovered GPL baseline and nxgl sources are pinned by `source-manifest.sha256` (435 source files). This repository publishes **our GPL-3.0 overlay** `wol-adapter.patch`; it does **not** contain the external recovered-source tree, owner Switch image, proprietary NSO/RomFS or generated shaders. The isolated `build_horizon.sh` verifies that manifest, copies the baseline, applies the patch and cross-builds the candidate. See [upstream source](../docs/upstream-source.md) and [current optimization roadmap §25](../docs/optimization-roadmap-active-native-unity-2026-10-29.md#25-full-repo-optimization-re-audit--2026-10-30).

**Latest full-audit status (reviewed HEAD `04384a73`, 2026-10-30):** the experimental Horizon v327680 runtime is developed separately from the installed Unity/Mono game. The [latest GitHub Actions run 41044438709](https://github.com/ruslan-k/west-of-loathing-portmaster-tsps/actions/runs/41044438709) is still **red**: one of the memory/source contract tests assumes a single `--- a/` section per path but the cumulative overlay has 125 such sections / 116 unique old-file paths. `git apply --numstat` parsed successfully; ARM64 compiler/QEMU and later tests were **skipped**, and public CI lacks the manifest-pinned recovered baseline to run a complete apply/build. Preserve source/sparse integrity while canonicalizing overlay sections or validating ordered repeats plus byte parity. **New independent B1 blocker:** [H-D1 two rebuilt ELF attempts](../evidence/horizon-hd1-2026-10-30/README.md) fail before gameplay on `segment size mismatch rtld.text.seg`; the known-good ELF passed on the same probe files. H-D1's local patch/header is **not part of this published overlay**, and its test can skip when the owner-local header is missing. Resolve effective loader flag, expected vs actual segment size/path and build identity; never disable the fail-closed size check. See [authoritative §26](../docs/optimization-roadmap-active-native-unity-2026-10-29.md#26-complete-optimization-follow-up--head-04384a73-2026-10-30).

**Performance state:** matched release-like Horizon gameplay at ~40.2–40.6 ms per 60-frame mean, not 30 FPS. Recent `NVN_DRAW_SPLIT` and `WOL_SAMPLE_SPLIT` diagnostics point toward sampler preparation but combine draw opcodes and report wall time, not opcode-exclusive CPU: see [c5–c8 evidence](../evidence/horizon-e1c-abc-2026-10-30/README.md). The proposed next default-OFF sampler-owner CPU attribution is **not** in this patch yet. Do not bypass `zero_texture_refresh` or render-target materialization in the quiet texture-pick path based solely on `real_sample=0`: those operations may have later coherence or fail-closed effects.

Older accepted experiments and `UpRender` 720p rewrites described in [historical Horizon notes](../docs/tsps-horizon-adapter.md) belong to their original build/version. On v327680 metadata v24 the earlier v23 force-width/height offsets are **not established**; the observed 16/9 fields are aspect ratio, and the current `ZERO_RENDER_SCALE` trial yielded a black KMS image. No default-on resizing or async frame optimization is accepted. The 65,536 KiB `CmaFree` admission gate remains in force; runtime gameplay CMA often falls to ~0, so extra GPU targets/snapshots need a separate measured memory-owner proof.

This is a **source and documentation statement**, not a new execution result. The native Unity/Mono production port and its user data, audio and saves are outside this Horizon overlay.
