# H-X1 — no-copy alias feasibility for the 1280×720 frame copy (roadmap §28 Gate 2)

Read-only design spike. No device run, no code change: the question is whether the guest's
`source 2 → destination 82` copy can become a GL alias instead of a CPU copy + upload.

## What the objects actually are (measured, `diag-gpu1.log`)

```
NVN_TEXTURE_REAL object=0xbbaffb8 format=0x25 size=1920x1080 levels=1 bytes=8294400 texture=2 depth=0
WOL_PRESENT_SOURCE slot=0 guest=0xbbafef8 texture=1 id=2 1920x1080 levels=1 frame=0
WOL_PAIR_TEX quiet-pick slot=0 id=82 1280x720
WOL_COLOR_COPY source=2 destination=82 region=1280x720@0,0->0,0 mode=copy-1:1
```

| | id=2 (source) | id=82 (destination) |
|---|---|---|
| Format | `0x25` | `0x25` |
| Dimensions | **1920×1080** | **1280×720** |
| Bytes | 8,294,400 | 3,686,400 |
| Role | NVN window/present source | sampled sprite sheet (quiet pick) |

## Verdict: BLOCKED — the object graph precludes an alias

- The copy is not 1:1 storage: it crops the top-left 1280×720 out of a 1920×1080 surface into a
  separately allocated 1280×720 texture.
- GLES2 has no texture views at all; GLES3 `EXT_texture_view`/`OES_EGL_image` require identical
  format **and** full-surface lifetime, and neither expresses a sub-rectangle alias. `glBlitFramebuffer`
  needs a draw-target pair of the same format and is a copy anyway (GPU-side), not an alias.
- The destination also carries a CPU mirror that later guest reads observe, so an alias would have to
  preserve CPU-visible bytes at the *source* stride, which a 720p view cannot represent.

Per §28's stop rule (“Stop BLOCKED if the object graph precludes alias”), the strict-v327680 branch has
**no alias escape** for this copy.

## What this leaves

- `WOL_COPY_GPU` (GPU blit) already measured: 42.37 → 40.78 ms (−1.6 ms frame, −3.3 ms CPU), below the
  3–4 ms bar.
- The only remaining structural idea is to stop the 1080p surface from existing at all, so the copy is
  1:1 or disappears with the present handoff. That is a guest-side size question (why the NVN window is
  1920×1080 while `Screen` answers 1280×720), not a runtime copy optimisation, and the 960×540 variant
  of that idea died on `T2_MEMORY_FLOOR` before gameplay.
- The honest conclusion matches the roadmap: the copy pathology cannot be removed from the runtime side
  alone, so the ≥30 fps target on this branch has no quantified remaining lever.

## Reviewed for reuse: wild1walker/portmaster-cuphead `codepatch`

That project ships a Mono.Cecil patcher for the **managed** PC assembly (`Assembly-CSharp.dll`), so it
cannot touch a Switch NSO. Three ideas are still worth recording:

1. `dlc-from-gog-install` / `steam-dlc` — entitlement is patched at managed level so the store copy
   reports the DLC as owned. Relevant to the Unity branch's "normal DLC entry" gate, not to Horizon.
2. `fonts-lazy` — defers font atlas build out of the load path: fewer stalls at scene entry.
3. `blur-idle`, `Effects.RenderBlurGamma`, `Glow` — skip post-process passes whose output is not
   visible that frame. This is the same class of win we need for the *stutter* complaint (load/transition
   spikes), and it is a managed-IL change, so again Unity-branch only.

None of the three is applicable to the Switch runtime; they are recorded here so the Unity branch is
not re-audited later.
