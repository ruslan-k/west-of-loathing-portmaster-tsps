# M6 gate: native ASTC upload and decode acceptance on the device (PROVEN, 2026-10-16)

Roadmap section 6, step 2 — "prove `glCompressedTexImage2D` acceptance for the chosen
ASTC mode on one texture and inspect actual driver allocations". Acceptance **and**
bit-accurate decode are now proven on the real device. This lifts the main technical gate
identified in `staging.md` (M9 only ever produced an in-bundle format probe; this is the
GLES path the M6 side-cache will use).

## Method

`tools/wol_astc_probe.c` (built for aarch64 in the same cross container as the runtime):

- GBM platform + EGL **pbuffer** context — no window, no page flips; the MainUI owner
  process is not disturbed and scanout is untouched. (The plain EGL default-display path
  fails with `EGL_NO_DISPLAY` on this firmware; the SDL path would open a fullscreen
  window — both rejected for this probe.)
- Two payloads (`tools/astc_data.h`, `tools/astc_data_96.h`, generated by
  `tools/wol_astc_probe_gen.py` from synthetic patterns; ASTC 6x6, `-medium`):
  - 64x64 → 11x11 blocks → 1,936 B, uploaded with `glCompressedTexImage2D`;
  - 96x96 → 16x16 blocks → 4,096 B, uploaded both directly and via the ES3
    `glTexStorage2D` + `glCompressedTexSubImage2D` path.
- Each texture is rendered over the full pbuffer with a quad and read back via
  `glReadPixels`; the readback is dumped as PPM and compared offline against the
  reference decode of the same `.astc` bytes by `astcenc -dl` (arm astcenc v4.7.0).

Build/run (device `tsps`, root):

```
docker run --rm --security-opt label=disable -v <spike>:/workspace --entrypoint /bin/sh \
  pmjs-arm64-spruce-local:20261002-gcc10 \
  -c 'aarch64-linux-gnu-gcc -O2 -DMESA_EGL_NO_X11_HEADERS /workspace/astc-work/wol_astc_probe.c \
      -o /workspace/astc-work/astc_probe -lEGL -lGLESv2 -ldl -lm'
scp astc_probe tsps:/mnt/UDISK/astc-work/ && ssh tsps 'cd /mnt/UDISK/astc-work && \
  LD_LIBRARY_PATH=/usr/lib ./astc_probe 2'
```

## Instrument notes (learned, worth keeping)

- `GL_COMPRESSED_RGBA_ASTC_6x6_KHR` is **0x93B4**; 0x93B0 is the 4x4 variant. The driver
  returns `GL_INVALID_VALUE` when `imageSize` does not match the format's block math — a
  cheap, strict gate we can rely on in the runtime cache to detect bad input early.
- EGL display prerequisites on this firmware: GBM platform via `eglGetPlatformDisplayEXT`
  works headless; `EGL_DEFAULT_DISPLAY` alone does not; SDL opens a window.
- Requested ES2 context reports `OpenGL ES 3.2` and accepts ES3 storage calls too
  (verified in the T3 path).

## What remains in M6 (roadmap section 6, steps 3-4)

1. Build the owner-local content-hash cache outside UnityFS (BC/DXT → ASTC 6x6 for static
   immutable payloads; keep RGBA fallback for dynamic/render-target/partially-updated
   assets). Builder + format + first 24-texture cache: **done** (`tools/wol_m6_cache_build.py`,
   `cache-design.md`, `cache-audit-24.json`). The runtime first-upload hook and its fallback
   remain the open step.
2. Driver-allocation inspection: only acceptance was measured here. The debugfs node
   `/sys/kernel/debug/mali0/gpu_memory` (mountable on demand; not mounted by default)
   reports per-context bytes and is a usable instrument, but a snapshot must be taken
   while the probe's textures are alive (the probe exits and frees them). Fold this into
   the first cache-validation pass with a paused probe or an in-game comparison.
3. Validation pass on the real renderer with physical captures, PSS/SwapPSS and reload
   latency, as the roadmap requires before any adoption claim.
